## Journeys at a glance

The sandbox answers with Teal's mock providers, stand-ins for the real payroll, Direct Connection, HMRC and payslip sources. Each test persona is a named applicant whose data you know in advance, so you can run a journey end to end and check what comes back.

Pick one of the four happy paths. Every one can be run through the API with your API key, or in the hosted webapp by opening the user's `webapp_link`.

| # | Journey | Persona | You enter | What comes back | Webhook |
|---|---|---|---|---|---|
| 1 | [Direct Connection](#path-1-direct-connection) | `direct-monthly-covered` | Sarah Chen, NI number AB654321C, born 1990-04-22, postcode E1 6PG | `201` with the applicant's monthly payroll, no sign-in needed | `user-payroll-submitted` |
| 2 | [User Connection](#path-2-user-connection) | `scraper-full-window-nomfa` (BrightPayCloud), or `scraper-full-window` (CGI, with a code step) | Sign in with the persona id as the user name and any password. CGI also asks for the code `123` | `201` with the account `Authorised`, then the payroll under `GET /payroll/{user_id}` | `user-payroll-submitted` |
| 3 | [Payslip upload](#path-3-payslip-upload) | `payslips-cover-window` | Three generated payslip PDFs | `201` with the payslips read, one payroll submission per payslip | `user-payroll-submitted` |
| 4 | [HMRC (Gov Connect)](#path-4-hmrc-gov-connect) | `hmrc-employed-authorised`, or `hmrc-self-employed-authorised` | NI number QQ000001A with flow `non_mtd`, or QQ000002A with flow `mtd` | `201` with the account `Pending` and an `authorization_url`, then the income under `GET /gov-connect/{user_id}` | `user-gov-connect-data-submitted` |

## Initial Setup

### API Key & Callback URL

Before you begin testing, ensure you have the following:

- An API key for authentication: please ask your Teal connection to supply you with an API key
- A callback URL for receiving webhook notifications: generate your URL in [webhook.site](https://webhook.site/)

### Webhooks Setup `/webhooks`

Subscribe to the events the happy paths send. The four paths send `user-payroll-submitted` (paths 1 to 3) and `user-gov-connect-data-submitted` (path 4).

```bash
curl --request POST \
  --url https://api.sandbox.goteal.co/webhooks \
  --header 'Content-Type: application/json' \
  --header 'X-API-KEY: <api-key>' \
  --data '{
  "events": [
    "user-payroll-submitted",
    "user-gov-connect-data-submitted"
  ],
  "name": "sandbox-happy-paths",
  "url": "https://webhook.site/00000000-0000-4000-8000-000000000000"
}'
```

Replace the `url` with your own webhook.site address: the sandbox refuses a URL that is not `https` or whose host does not resolve to a public address. A webhook `name` must be unique.

<Note>
  Optional fields: `signing_secret` (for HMAC verification), `encryption_key`
  (for AES/GCM payload encryption), `config.include_payload` (to include the data in the delivery).
  See [Webhooks](/api-reference/webhooks) for the events and their payloads.
</Note>

**Response Example:**

```json
{
  "webhook_id": "95a0e70b-fe02-4f47-aef9-2efff279df71",
  "events": ["user-payroll-submitted", "user-gov-connect-data-submitted"],
  "name": "sandbox-happy-paths",
  "url": "https://webhook.site/00000000-0000-4000-8000-000000000000",
  "created_at": "2026-11-19T00:00:00.000Z"
}
```

### Configure Client Settings `/configuration`

Configure client-wide settings. The happy paths need the sources they use switched on: `payroll_connections_enabled` for path 2, `payslip_upload_enabled` for path 3 and `hmrc_enabled` for path 4. Direct Connection (path 1) is always on. `PATCH` changes only the fields you send.

```bash
curl --request PATCH \
  --url https://api.sandbox.goteal.co/configuration \
  --header 'Content-Type: application/json' \
  --header 'X-API-KEY: <api-key>' \
  --data '{
  "payslip_upload_enabled": true,
  "payroll_connections_enabled": true,
  "hmrc_enabled": true,
  "payroll_period_months": 12
}'
```

**Response Example** (shortened to the fields you set):

```json
{
  "payslip_upload_enabled": true,
  "payroll_period_months": 12,
  "hmrc_enabled": true,
  "payroll_connections_enabled": true,
  "warnings": []
}
```

<Note>
  `GET /configuration` reads the settings back. Recurring checks are configured here too
  (`recurring_checks_enabled`, `recurring_check_frequency`, `recurring_check_duration_days`);
  in sandbox you can test the `HOURLY` frequency (not available in production).
</Note>

## User Setup

Every path starts the same way: create the applicant, generate a token for them and record their authorisation. Create one applicant per persona, with the details the path gives.

#### Create a User `/users`

Create the user with the persona's details exactly as listed: the Direct Connection lookup matches on name, date of birth, NI number and postcode. This example is Sarah Chen, the persona of path 1:

```bash
curl --request POST \
  --url https://api.sandbox.goteal.co/users \
  --header 'Content-Type: application/json' \
  --header 'X-API-KEY: <api-key>' \
  --data '{
  "forename": "sarah",
  "surname": "chen",
  "ni_number": "AB654321C",
  "date_of_birth": "1990-04-22T00:00:00.000Z",
  "post_codes": ["E1 6PG"],
  "payroll_period_months": 12
}'
```

**Response Example:**

```json
{
  "user_id": "95a0e70b-fe02-4f47-aef9-2efff279df71",
  "forename": "Sarah",
  "surname": "Chen",
  "ni_number": "AB654321C",
  "date_of_birth": "1990-04-22T00:00:00.000Z",
  "post_codes": ["E1 6PG"],
  "payroll_period_months": 12,
  "created_at": "2026-11-19T00:00:00.000Z"
}
```

`payroll_period_months` is the lookback of the check, in months. Creating the same name, date of birth and postcode twice answers `409`: delete the user (see [Cleanup](#cleanup)) or add a different `ext_id`.

```bash
curl --request POST \
  --url https://api.sandbox.goteal.co/user-tokens \
  --header 'Content-Type: application/json' \
  --header 'X-API-KEY: <api-key>' \
  --data '{
  "user_id": "95a0e70b-fe02-4f47-aef9-2efff279df71"
}'
```

**Response Example:**


#### Connect a Payroll Account `/accounts`

This is the user signing in to their payroll account. The payroll is retrieved as part of the connection.

```bash
curl --request POST \
  --url https://api.sandbox.goteal.co/accounts \
  --header 'Content-Type: application/json' \
  --header 'X-API-KEY: <api-key>' \
  --data '{
  "user_id": "95a0e70b-fe02-4f47-aef9-2efff279df71",
  "payroll_provider": "brightpaycloud",
  "user_name": "scraper-full-window-nomfa",
  "password": "any-password"
}'
```

**Response Example:**

```json
{
  "account_id": "3c1f0d52-6a9e-4b7d-9f13-8e2a5b4c7d90",
  "payroll_provider": "brightpaycloud",
  "user_name": "scraper-full-window-nomfa",
  "created_at": "2026-11-19T10:32:00.000Z",
  "status": "Authorised"
}
```

<Note>
  Optional fields: `from` and `to` (ISO 8601 date-times) to filter the payroll retrieved, and
  `extra_login_params` for provider-specific login fields (omit it when it isn't required).
</Note>

`payroll_provider` is one of the nine [providers](#providers). The payroll is the recorded data of the persona, not generated, and the user name decides which persona answers.

**With a code step (CGI, `scraper-full-window`):**

```bash
curl --request POST \

  "payroll_provider": "cgi",
  "user_name": "scraper-full-window",
  "password": "any-password"
```


Send the code `123` to complete the connection:

```bash
curl --request PUT \
  --url https://api.sandbox.goteal.co/accounts/7a2e9b14-0c58-4d36-8f61-2b9d3e5a1c47/mfa \
  --header 'Content-Type: application/json' \

  "mfa": "123"
```

The response is `200` with the account and `"status": "Authorised"`; the payroll is retrieved at that point.

#### Retrieve the payroll `/payroll/{user_id}`

Read the payroll with your API key. The submissions are the persona's monthly pay.

```bash
curl --request GET \
  --url https://api.sandbox.goteal.co/payroll/{user_id} \
  --header 'X-API-KEY: <api-key>'
```

See [Retrieve Payroll Data](#retrieve-payroll-data-payroll) for the response.

#### Retrieve latest payroll `/payroll/entries/connections`

To ask a connected account for new payroll again, call this endpoint with the user's bearer token. It fetches and stores the payroll and answers with the count only, not the payroll data:

```bash
curl --request POST \
  --url https://api.sandbox.goteal.co/payroll/entries/connections \
  --header 'Authorization: Bearer <bearer-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "account_id": "3c1f0d52-6a9e-4b7d-9f13-8e2a5b4c7d90"
}'
```

**Response Example:**

```json
{
  "payroll_submissions_count": 12
}
```

Returns `201 Created` when at least one submission was retrieved, or `200 OK` with `"payroll_submissions_count": 0` when none was. To read the data, use `GET /payroll/{user_id}` with your API key.

## WebApp Usage

Teal's webapp can be tested by accessing `https://app.sandbox.goteal.co/` in the browser.

### Launching the webapp for a user

When you create a user token via `POST /user-tokens`, the response includes a `webapp_link` field:

```json
{
  "token": "eyJhbG...",
  "webapp_link": "https://app.sandbox.goteal.co/r/ZwgQkNEMZ4QDkQ",
  "created_at": "2026-11-19T10:30:00.000Z"
}
```

Open (or redirect the user to) the `webapp_link` URL. This establishes an authenticated session via a secure HttpOnly cookie and redirects the user into the webapp. No token appears in the final URL.

### Embedding in an iframe

When embedding the webapp in a cross-origin iframe, `SameSite=Lax` cookies are not available (all modern browsers block cross-site cookie access in iframes). The webapp handles this automatically via the **postMessage protocol**:

1. The webapp loads and detects it is embedded (`window !== window.parent`).
2. It posts `{ type: "teal:session_required" }` to the parent window (origin-restricted to the `callback_url`).
3. The parent responds with `{ type: "teal:session_token", token: "<jwt>" }` using the `token` from the `/user-tokens` response.
4. The webapp uses the token as an in-memory `Authorization: Bearer` credential for all API calls within that iframe session.

Your parent page must include a message listener:

```javascript
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://app.yourdomain.goteal.co') return;
  if (event.data?.type === 'teal:session_required') {
    event.source.postMessage(
      { type: 'teal:session_token', token: YOUR_JWT_TOKEN },
      event.origin
    );
  }
});
```

Set the iframe `src` to `https://app.<env>.goteal.co/?callback_url=<your-parent-origin>`. The `callback_url` parameter tells the webapp which origin to trust for the postMessage exchange.

<Note>
  The token is held in memory only — it is never persisted to cookies, localStorage, or sessionStorage within the iframe. The session lasts for the lifetime of the iframe. If the iframe is destroyed and re-created, the parent must respond to a new `teal:session_required` message.
</Note>

For clients that configure a `client_callback_url`, the webapp also communicates journey outcomes back to the parent page via `postMessage` (type: `teal:journey_outcome`).


You can test the webapp with any of the personas of the [four happy paths](#journeys-at-a-glance), or any other from [Test personas](/test-personas).
